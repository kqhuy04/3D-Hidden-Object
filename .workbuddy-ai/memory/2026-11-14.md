## DESIGN GACHA — standalone mini-game + Blender MCP connection

User asked to try a gacha game from a reference image and pointed out Blender on
their machine could be connected. Two deliverables, both **outside** Photo Hunt's
game code (the standing "polish the existing game, do not add modes" rule).

### 1. Blender MCP on this machine (the reusable part)

- Blender **5.2** at `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe`
  (4.5 also installed, but the MCP addon lives only in the 5.2 config).
- Addon: `AppData/Roaming/Blender Foundation/Blender/5.2/scripts/addons/blender_mcp.py`.
  The MCP server (`~/.workbuddy-ai/mcp.json`) expects `BLENDER_HOST=127.0.0.1`,
  `BLENDER_PORT=9876`.
- **Auto-start does not fire on a plain launch** — the addon registers a
  `load_post` handler that only runs when a file is loaded. Launch with a
  `--python` script that enables the addon and calls
  `bpy.ops.blendermcp.start_server()` instead.
- `tmp-blender-mcp-start.py` in the repo root does exactly that and writes
  `tmp-blender-mcp.log`. Blender's GUI stdout is not visible from Bash on
  Windows, so the script must write its own log file.
- Update the addon with `uvx mcp-for-blender install-addon`, then restart
  Blender (protocol 15 → 16, addon 1.8 → 2.0).

### 2. The gacha game — `gacha/`

- `gacha/build_machine.py` models the machine in bpy and exports
  `gacha/assets/gacha-machine.glb` (939 KB, 71 objects). Rebuild by
  `exec(open(...).read())` inside the connected Blender.
- `gacha/poster/poster.html` → `render-poster.mjs` → `assets/poster.png`: the
  DESIGN GACHA poster, drawn as HTML/SVG and screenshotted with the repo's
  `tools/cdp.mjs` Chromium driver. Free alternative to ImageGen.
- `gacha/src/` is a standalone Vite app (reuses the root `node_modules`):
  `./node_modules/.bin/vite --config gacha/vite.config.ts` → port 5180.
- `gacha/shoot.mjs` plays a full pull headlessly and writes `gacha/shots/`.

### Blender gotchas that cost time

- `primitive_cone_add` takes `radius1`/`radius2`, **not** `radius`.
- glTF export is Y-up: Blender +Z → glTF +Y, Blender −Y (front) → glTF +Z.
  So a knob whose axis is Blender Y has its axle on glTF **local Z** — spin it
  by multiplying the node quaternion with a local-Z rotation, not by animating
  `rotation.z` on a node whose own rotation is (90°, 0, 0).
- Blender → glTF hierarchy: parent parts in Blender (`matrix_parent_inverse =
  parent.matrix_world.inverted()`) or the game has to move them one by one.
- Blender 4.x/5.x `scene.render.engine` id is `BLENDER_EEVEE_NEXT`; the old
  `BLENDER_EEVEE` id raises `TypeError`.

### Game tuning learned in the harness

- Tween timing must use **wall-clock** dt, not a clamped physics dt: headless
  SwiftShader runs at ~8 fps, and a 0.05 s clamp stretched a 1.7 s turn into
  6 s. The harness stalled on "Turning..." until this was split.
- The reveal card must not cover the scene — it is docked top-right with no
  scrim, and it appears 0.9 s after the prize pops so the pop is visible.


## Gacha machine — second redesign pass (feedback round 2)

The user rejected the rotary knob and the protruding chute. Final design:

- **Start control is a plain push button**, not a knob. `ButtonBase` (collar) +
  `ButtonDome` (mint hemisphere, Blender scale Y 0.62 so it is a shallow dome).
  The dome sinks 0.045 into the collar and springs back with a small overshoot.
  Radius 0.145 keeps it inside the 0.32-tall panel plate — at 0.16 it poked
  0.02 above the panel and read as sliding off.
- **The ball exit is a hollow arch cut into the cabinet front**, not a tube.
  Order matters: hollow the cabinet first, *then* cut the arch with
  `use_self=True`, or the cut leaves a face across the cavity.
- **Glass on front, left and right only** — the chamber shell is hollowed and
  three panes dropped in; the back stays solid.
- Palette brightened twice: rose `#8E6260` body, mauve coin plate, mint button.

### Delivery, in glTF space

A capsule starts at `SHELF_TOP + r`, falls through the drop hole to
`CAVITY_FLOOR + r` (y 0.425), rolls forward to `ARCH_MOUTH_Z` (z 0.44), then
falls to the floor and rolls to `REST_Z` 0.95. Anchors are constants in
`src/machine.ts` mirroring `build_machine.py` — moving one without the other
silently floats or sinks the capsule.

- The arch mouth is at z 0.44 and the plinth edge at z 0.50, but the capsule
  clears it: at 1.15 m/s it has only dropped 0.015 by then.
- **Clamp the roll to `REST_Z`** rather than letting friction decide. Friction
  plus two bounces put it at z 1.15, on top of the decorative floor capsules.
  Those moved out to x −1.02 / −0.84 / +0.95, clear of the x −0.28 lane.
- A **dim point light inside the cabinet** (0.28 cd, distance 1.15) is what
  makes the arch read as depth; without it the cavity is pure black and the
  opening looks like a panel painted on the front.
- A front-facing fill (0.95 from −2.4, 2.4, 4.8) matters more than raising the
  sun: the sun rakes the front face, so the model rendered much darker than the
  Blender preview until the fill was aimed at it.

### Harness

`shoot.mjs` now **polls for the phase** instead of sleeping. Headless is
~2.5 fps here (17 frames in 7.3 s), so a pull that takes 1.5 s on a real GPU
takes ~18 s headless and any fixed sleep is a coin flip.

### Dead code removed

The poster was cut from the machine early on, so `gacha/poster/` and
`assets/poster.png` were deleted — the GLB has **0 images / 0 textures**, all
11 materials are flat colours. Prize copy that mentioned the poster was
rewritten to match.

## Gacha machine — third pass: one pipe, a closing hatch, fewer balls

User rejected the hollowed cabinet ("đừng rỗng hết phần dưới") and asked for the
shelf hole and the exit to be **one hollow pipe**, with the hole **closed until
the player presses the button**.

- Cabinet is solid again. A 0.40 square `Shaft` (z 0.30..1.20) drops from the
  shelf and meets a 0.38 × 0.36 `Tunnel` that runs forward out of the arch.
- **Three objects cap that bore if you forget them** — all created after the
  cabinet was cut, so each needs its own pass: `CabinetLedge` (z 0.97..1.07),
  `GlobeShell`'s floor (z 1.04..1.10, which sits *inside* the shelf) and the
  shelf itself. Found with `scene.ray_cast` up the shaft, not by eye: the
  render looked fine because the blocked bore was dark on dark.
- Hatch: `HoleHatch` parented to a `HatchHinge` empty at the hole's rear edge.
  Closed it covers a 0.30 hole; `rotation.x = +90°` swings it down the shaft's
  rear wall. Measured clearances: plate at y 0.209..0.235, falling capsule at
  y ≤ 0.185, shaft wall at y 0.260.
- **A disc hinged at its rim cannot swing inside a bore of similar size** — it
  always clips the wall. The shaft had to be wider than the hatch (0.40 vs
  0.34) for the swing to work at all. Don't try to shrink the shaft.
- Hatch uses the **same material as the shelf on purpose**: closed it reads as
  one solid floor and the hole only appears when it swings. A contrasting plate
  made the closed state look like a permanent hole.
- Button: one joined cylinder + shallow sphere cap, radius 0.10, flat shaded.
  The old dome-on-a-collar had a separate 0.145 base that poked past the panel
  edge and read as a display artifact at the seam.

### Toss + hatch choreography (`pressButton`)

Toss tween 0.95 s (lift `sin(π·t)`), hatch opens at 0.55 s, dispense at 0.92 s,
hatch closes 0.55 s after dispense. Per-capsule `globePhase` varies the hop so
the pile doesn't rise as a slab, clamped by headroom under `CHAMBER_CEILING`.

**Bug found:** the toss froze the pile in mid-air. The tween's `onDone` zeroes
`globeToss`, and `updateGlobeJitter` is guarded on `globeToss > 0.001`, so the
last frame never ran and the capsules stayed lifted. Fixed by snapping each
capsule back to `globeBase` inside `onDone`.

Pile cut from 21 to 14 capsules — the old one overflowed the glass.

### Harness lesson

Screenshots cost 1–2 s each in headless SwiftShader, and the hatch is only open
~0.9 s. Polling *after* a screenshot always misses it. Poll first, shoot second;
and a transient like the toss needs its own run with the screenshot queued at a
fixed delay instead of after a poll.

## Gacha machine — fourth pass: the pile bursts, it does not jitter

User: "các quả bóng bắn tứ tung lên cơ, chứ ko phải rung rung như hiện tại".
The old `updateGlobeJitter` only nudged positions by ±0.015 and hopped them on
a shared sine — it read as vibration, not a throw.

Replaced with a real burst (`updateGlobeBurst` in `src/main.ts`):

- Each capsule gets its own `vel` and `spin` on press, then integrates gravity
  (7.0) and bounces off the chamber's inner box with per-axis restitution.
- **`separateBalls` is what makes it read.** Without a two-pass push-apart the
  thrown pile passes through itself and looks like one lumpy mass, not balls.
  O(n²) over 14 balls is free.
- After `BURST_FLY` (0.75 s) the balls ease back on an exponential
  `1 - exp(-dt*9)` toward their shelf positions, so every pull starts from the
  same pile. Frame-rate independent, no snap.
- The box constants (`GLOBE_X` 0.395, `GLOBE_Y_FLOOR` 1.285, `GLOBE_Y_CEILING`
  1.775, `GLOBE_Z_BACK` -0.235, `GLOBE_Z_FRONT` 0.307) are the chamber inset by
  the capsule radius — the one place model dimensions are duplicated in code.

Timeline is now: burst 0 → hatch opens 0.66 s → dispense 1.02 s.

**Capturing a transient in headless:** at a 900×760 viewport SwiftShader is
fast enough to finish the 0.75 s burst before a screenshot lands (~0.5–1 s), so
every capture showed the pile already settled. `Emulation.setCPUThrottlingRate`
rate 12 drops the frame rate, the clamped `dt` turns the burst into slow
motion, and the frames become photographable. Use that instead of editing
durations for a screenshot.

## Gacha machine — fifth pass: the heap stays scattered

User: "xong rồi thì đừng xếp về như cũ nữa, vẫn phải để nó lung tung ngẫu nhiên
đi mới có cảm giác của máy gacha". The burst was right; the *reset* was wrong.

`globeBase` is gone. The pile now keeps whatever the burst gave it:

- `BURST_SETTLE` became `BURST_FALL` (0.6 s): gravity still pulls, but the
  sideways drift bleeds off on `exp(-dt*6)` so nothing slides for ever.
- `packPile` then drops each capsule onto the shelf or onto the ball under it
  (`y = q.y + sqrt(d² - horiz²)`), sorted lowest first. x/z and rotation are
  left exactly as the burst left them — that is what makes each heap different.
  It also pushes any capsule off `DROP_HOLE` by `CAPSULE_RADIUS + 0.065`, or the
  machine has nothing to drop.
- `unjam` slides apart pairs that `packPile` had to clamp at the ceiling;
  `packPile`/`unjam` alternate up to five times.

**Each capsule is also thrown outward from the middle of the heap.** Without
that the pile erupts in the corner it was already sitting in and every pull
leaves the same clump — the scatter has to spread, not just jiggle.

### Fourteen was too many once the packing was random

A neat 8+4+2 stack fits; a *random* pack of the same 14 balls fills the chamber
floor to ceiling (measured ySpan 0.490 of 0.490) and reads as jammed — the exact
complaint that cut 21 to 14 in the first place. Modelled pile cut to **11**
(7+3+1, explicit coordinates in `build_machine.py`). Measured after the change:
ySpan 0.20–0.36, `outOfBox` 0, overlapping pairs 0.

### Two things worth keeping

- **Glass must not cast shadows.** `traverse` set `castShadow` on every mesh,
  and a transparent material still blocks the sun completely — the chamber was
  flatly lit and the heap had no contact shadow, so the capsules read as
  hovering. Now `castShadow = !name.startsWith('Glass')`.
- **`window.__gacha.balls()`** returns every chamber position. A probe that
  measures `outOfBox` / overlapping pairs / `ySpan` proves the pile settled
  correctly in numbers; screenshots alone cannot tell "resting" from "floating".

**Harness lesson:** the reveal card only appears ~0.9 s of *tween* time after
`open()` — several wall seconds on SwiftShader. A fixed `sleep(1800)` clicked
Close before the card existed, so it stayed open and the next pull timed out
waiting for `await`. Poll for `reveal.hidden === false`, click, poll for `true`.

## Gacha machine — sixth pass: the reveal

User asked for a proper open: "khi quả trứng rơi xuống, thì sau đó quả trứng sẽ
hiển thị ở giữa màn hình, rồi mở ra, rồi phần quà trên trong xuất hiện, quả trứng
lùi về sau rồi fade dần, phần quà thì có tên, độ hiếm + ánh hào quang tùy màu,
và người chơi có thể xoay phần quà được." Choices confirmed with the user:
camera stays put, the name plate keeps name + rarity (the note line and both
buttons are gone), drag rotates freely with a slow auto-spin.

- **Put the capsule on the camera's own axis.** `camera.position +
  camera.getWorldDirection() * 1.5` projects to NDC (0, 0) exactly — dead centre
  whatever angle the player is looking from. Measured it; do not eyeball it.
- **The creature's origin is at its feet.** Its visual centre is ~0.22 above the
  origin, so the prize has to sit *below* the anchor (`anchor.y - 0.22`) or it
  appears high on the screen. This was the first bug: the bear looked 130 px
  above centre even though its position projected to NDC 0.
- **The name plate must not take pointer events**, or it swallows the drag.
  `.reveal-card { pointer-events: none }` — and the old guard
  `if (ui.drawerOpen || ui.revealOpen) return` in the pointer handler had to go
  with it.
- `OrbitControls.enabled = false` while a prize is on screen, so the
  composition holds; the drag on the canvas turns the prize instead.
- The halo (`buildHalo`) is a flat disc + hard ring + 16 rays in the **rarity
  colour** — the softer `RARITY_GLOW` tone was invisible on the cream
  background, which is how the first attempt looked like nothing at all.
- The shell retreats along the camera's backward vector and fades
  (`fadeGroup`); the halo blooms during the same beat.
- The prize flies home to the floor when the next coin goes in, and joins the
  collection shelf there.

**Harness lesson:** the game needs several seconds to fetch and parse the GLB
before `window.__gacha` exists on a software renderer. Driving the game before
the hook is up fails with a bare "undefined" error. Every harness must wait
for `typeof window.__gacha === 'object'` first — the pile probe hit this too.

## Seventh pass — the four fixes the user asked for

User, in one message: the egg opens the wrong way round (the opening must face
the viewer); the burst ends with a visible hitch and the capsules get
re-arranged; the glow should be a soft aura, not a ring (grey for common, blue
for rare); the prize must not auto-spin and must be tippable rather than pinned
at its base.

- **`packPile` was the hitch.** Any pass that re-positions capsules at the end
  of the burst is a teleport, and the user sees it. Deleted, along with `unjam`
  and the old `separateBalls`. `updateGlobeBurst` is now one integrator for both
  phases: separation **plus an impulse** (reflect the closing normal velocity,
  `BALL_BOUNCE = 0.18`), a funnel force toward the shelf centre while settling,
  and a rest test (`burstT > BURST_FLY + BURST_GATHER` and fastest speed under
  `BURST_REST_SPEED` for 0.2 s, or `BURST_SETTLE_MAX`).
- **The pile settled into one flat layer** — measured `ySpan = 0.00` over many
  pulls. The shelf is wide enough for all 11 capsules, so honest physics spread
  them to the glass and stopped. Weaker throws and a funnel did not help. The
  fix was to resolve **near-vertical contacts vertically** (`|ny| > 0.5` snaps
  the normal to ±Y) so an upper capsule is *lifted* instead of shoved aside.
  `ySpan` is now ~0.19. If the heap ever reads flat again, check that rule first.
- **The capsule was hinged nowhere.** `buildCapsule` now parks each dome inside
  a pivot at `z = -radius * 0.92` and exposes the pivots as
  `userData.topGroup`/`bottomGroup`. Rotating a pivot about X swings its front
  rim apart from the other — a mouth opening toward the camera. Rotating a dome
  about its own centre (what it did before) sweeps the rim across the capsule
  and reads as a hoop worn around the creature's head. Each half also gets a
  `BackSide` lining at `0.93 r` so the open shell looks hollow.
- **The creature is bigger than the shell** (0.34 wide vs 0.31 across), so it
  cannot be pulled out at full size. It emerges at `small = 0.55` and only grows
  to 1.0 once the shell has started leaving. Same reason the shell scale boost
  at the anchor dropped from 1.55 to 1.34.
- **The aura is ten faint discs, not a ring.** `buildAura` draws concentric
  `CircleGeometry` discs at `opacity 0.062`, each a hair behind the last so the
  blend order is fixed. No gradient — the flat steps *are* the falloff. The
  creature covers the middle of the stack, so only the outer two or three rings
  are ever seen; push the per-disc opacity up and they turn into a hard plate.
- **No auto-spin, and the tilt is free.** `revealDrag.idle` and the pitch clamp
  are gone; `prize.rotation.set(pitch, yaw, 0, 'YXZ')` plus an orbit about
  `PRIZE_CENTRE` (`pos = base + offset - offset.applyEuler(rot)`). Verified:
  rotation identical after 1.6 s idle, and a downward drag reaches pitch 3.64 rad
  (past upside down). `updateReveal` must short-circuit while
  `delivery.dismissing`, or it overwrites the fly-home tween's position.

**Screenshot lesson (cost me an hour):** headless Chromium only renders when
asked, so `Page.captureScreenshot` is what advances the frame — sleeps advance
nothing — and the frame it returns is the one already presented, i.e. it lags
the live state by an update. Timings read from a screenshot are therefore
fiction. To photograph a specific moment, stretch that beat for the take
(`tween(3.0, …)`) and revert afterwards. `window.__gacha.reveal()` now reports
the shell's scale/position/lid/bowl and the prize's scale/position so the
choreography can be checked numerically instead.

Also fixed in passing: `buildCapsule` ran its shadow traverse *before* attaching
the halves, so capsule meshes never cast a shadow at all.

## Eighth pass — the magnet and the shell in front of the prize

User: the capsules get sucked towards the middle after a burst, which looks
unnatural; and sometimes the two shell halves cover the prize when it opens.

- **The magnet was `HEAP_PULL`, a funnel towards the shelf centre.** It existed
  because an earlier, broken separation pass left the pile flat, and pulling the
  capsules together forced them to stack. Once near-vertical contacts were
  resolved vertically, the funnel was no longer needed — eleven capsules cannot
  fit on the shelf in one layer anyway. Deleted, along with `BURST_GATHER` and
  `HEAP_Z`. Measured over three pulls: `mean |x|` now *grows* through the settle
  (0.15 → 0.23 → 0.26 → 0.29), i.e. they spread, and `ySpan` stays ≈ 0.19.
  **Never add an attraction force to a pile the player is watching** — they can
  see it slide, and it reads as a magnet, not as physics.
- **The shell covering the prize was a sign error.** Beat 3 built its retreat as
  `-revealForward` and called it `back`. `revealForward` is the direction the
  camera *looks*, so the shell was flying **towards the lens** while fading —
  growing, and covering the creature. The retreat vector is `revealForward`
  itself. Check the sign on any "away from the camera" vector before believing
  the comment next to it.
- **Beat 2 now drifts the shell back 0.16** as it opens. The lower rim sits
  0.135 in front of the capsule centre and the creature's belly only 0.07, so
  the bowl was drawn across the prize's body even with the retreat fixed.
- `06-opening` in the harness needs `sleep(450)`, not 1600: a capture returns
  the frame already on screen, and the click-plus-capture overhead eats several
  hundred ms of the choreography. 1600 lands on the finished reveal.
- To photograph a beat reliably, stretch it for the take (`tween(3.0, …)`), shoot,
  then put the duration back. That is how the occlusion was confirmed fixed.

### Store facts checked (2026-11-14), for the eventual release

- Google Play: new apps must be **AAB**, not APK (since Aug 2021). New *personal*
  developer accounts must run closed testing with **12 testers for 14 days**
  before they can request production access.
- Microsoft Store accepts MSI/EXE, but **MSIX** is what gets free code signing
  and Store commerce. So MSI alone will not support selling coins.
- Selling virtual currency on either store **must** go through the platform's
  billing (Play Billing / Store add-ons) with server-side receipt validation.
  A self-hosted checkout is not allowed.
- One web build can be wrapped four ways: web (itch.io), PWA, TWA → AAB for
  Play, Tauri → MSIX for the Store. Do not port the game separately per store.
- Blocker for mobile: controls are WASD + pointer lock + wheel zoom. A touch
  scheme and a mid-range-Android performance pass are 1-2 weeks, not packaging.
- Licence is fine: `docs/THIRD_PARTY_NOTICES.md` permits commercial sale of
  games built on the Polyfork kits; only redistributing raw `.glb` is banned.

No code changed this pass. The user was gathering the lay of the land, not
asking for work yet.
